# 全仓文档盘点

仅在用户要求全仓 as-built 审计或广泛文档重整时读取并执行；局部同步不生成独立 gap 文档。

## 第 2 步：盘点仓库

先检查仓库，再决定应存在哪些文档。按实际存在情况检查：

- README、文档目录和智能体说明
- 领域词汇表、ADR 和决策记录
- 应用入口、用户路由、公开 API 和 BFF 路由
- schema、公开类型、认证、授权、会话和 Cookie
- 外部集成和环境变量校验
- Docker、Compose、Kubernetes、Helm、Ingress、Nginx 或同类部署文件
- 健康检查、就绪检查、日志、指标、追踪和诊断
- 单元、集成、浏览器、契约和冒烟测试
- 包管理或构建脚本、相关 Git 历史
- 本地可访问的议题和合并请求记录

使用项目配置确定优先级，但必须用实际文件验证配置。不要假定仓库遵循理想或常见架构，只记录真实存在的架构。

完成标准：已盘点相关实现与文档表面；重要公开和运维行为都有明确证据来源；审计基于仓库事实而非先前假设。

## 第 3 步：创建文档差距审计

广泛编辑文档前，创建或更新文档差距报告。优先使用项目配置指定的位置；未指定时使用：

```text
docs/audits/<date>-<scope>-documentation-gap.md
```

仓库已有更合适的约定时，遵循该约定。报告必须包含：

```md
# 文档差距审计

## 基线

- 仓库：
- 当前分支：
- 当前 HEAD：
- 基线：
- 基线提交：
- 范围：
- 已验证环境：
- 验证日期：

## 执行摘要
## 已验证行为
## 推断行为
## 未知项
## 过时文档
## 缺失文档
## 文档范围之外发现的风险
## 建议的文档变更
## 需要人工确认的问题
```

每项发现记录：分类、主张或缺失主题、实现证据、测试/部署/环境证据、受影响文档、规范所有者、建议行动，以及是否需要人工确认。不要把文件修改时间当作文档正确的证据。

完成标准：已分类所有相关现有文档；每项范围内的重要实现行为已有文档或被列为缺失；已识别过时主张；不受支持的主张标为推断或未知；未修改运行时文件。
