## 周报（周功能总结）

当用户说「周功能总结」「上周做了什么」「把上周做的总结下」「生成周报」时，**以本周日报为素材**汇总整周（上周一~上周日，或指定区间），按**功能维度**而非日期归并。参考 `周报/2026/8/第二周/周功能总结-0810-0816.md` 的写法。

### 周报生成流程

**素材优先级：先读本周日报，不要重新采集。** 日报是同一批提交的一手整理稿，且**已含周报要用的叙述**（每笔的问题→改动→验证、合并状态、分支表、票据归属、逐日口径说明）。重采一遍要重做同远端 / patch-id / stash / 无 ref 的全部去重，既慢又容易与日报口径打架。

1. **前置检查——本周每个自然日是否都有日报**。缺的日子**先按日报流程补生成**（这也是「先日报、后周报」的由来）；补齐后周报只剩下面两步。
2. **读本周日报**（`<输出根>/YYYY/M/第N周/MMDD.md`，逐日读）并按功能域归并：跨仓、跨日的同一功能合并为一节，主线在前。
3. **汇总每日数字**：日报之间是半开区间、互不重叠，笔数 / 文件 / 改动**直接相加**即可（天然规避重复采集的去重坑）。
4. **刷新合并状态与 MR 队列**（日报是历史快照，周报要当前值）：`git fetch --all --prune` 后只对**未合部分**重判 `git merge-base --is-ancestor <sha> refs/remotes/origin/HEAD`，并查一次当前开放的 MR。**不重采明细**。
5. **人员贡献**（若多人协作）：用 `git shortlog -sne --all` 统计作者分布，区分「总体」与「主要作者个人」。
6. **生成 Markdown 周报**，文件名如 `周功能总结-0810-0816.md`，写入对应周目录。

**只在以下缺口才回退到 git，且只查缺口部分**：

- 目标日期**没有日报**（或日报未覆盖该日）；
- 日报口径被质疑 / 自相矛盾 —— **定点复验那一处**，不重跑全量采集；
- 日报缺「原来怎样」而小结必须要 —— 定点看该笔提交或相关文档，并在文中注明来源。

> **不要为写周报 / 小结做的事**：重跑 `collect_commits.py` 全量采集、`git show --stat` 逐笔翻文件清单、为补背景读源码或 ADR。这些内容日报里都有；日报确实没有时，按上一条的第三个缺口定点补，而不是整轮重来。

### 周报模板

```markdown
# 周功能总结 YYYY-MM-DD~YYYY-MM-DD（第 N 周）

> 上周跨 N 个仓库共约 **M 笔**提交（无提交仓库标注）。实际活跃区间；主线概述（2-3 条，如「三大主线：告警中心通知域收口 / gateway 模块架构重构 / central Skill 体系打磨」）。

## 1. <功能域1>
> 一句话定位（如「本周绝对主线。前端把通知配置从 Mock 切到真实后端，后端同步落地」）。

- **子能力**：描述（`hash`）。
- **子能力2**：描述（`hash`）。

## 2. <功能域2>
……（跨仓库同一功能合并为一节，标注各仓哈希）

---

## 数据概览

| 仓库 | 本周提交 | 主功能 |
|---|---|---|
| project-a | ~N | … |
| project-b | ~N | … |
| project-c | ~N | … |
| project-d | ~N | … |
| project-e | 0 | — |

**一句话**：<整体概括上周三条主线与成果>

---

## 人员贡献（可选，仅多人协作时需要）

### 总体
<作者分布表：作者 / 仓库 / 提交数 / 主要负责>

**要点**：<主要作者占比、最重单点工作量、他人分工>

### <主要作者> 个人
按仓库拆开：<各仓库负责的功能域与大致笔数，呼应上面的功能域编号>
```

### 周报说明

- 周报**按功能域归并**，不按日期；跨仓库同一功能合并为一节，并在节内分别标注各仓 commit 哈希。
- 每节开头用 `>` 引用一句话定位该域的重要性（如"本周绝对主线"）。
- «数据概览»用表格列各仓库提交数与主功能；«人员贡献»仅在多人协作时追加，区分「总体」与「个人」。
- 文件名 `周功能总结-MMDD-MMDD.md`，与每日 `MMDD.md` 同目录（对应周子目录）。
- 若 `workItems.enabled`，可在周报末尾附「**Work Item 阶段分布**」小节，按 `stages` 汇总本周各 Work Item 当前阶段。
- **周报区间以工作日为界**：周报覆盖周一~周五，周末（上周六、日）提交按「周末提交归类」规则归入下周一日报，不在本周围报体现（见上方「注意事项」）。生成周报的采集区间若用整周 `since=周一首日 --until=周日+1`，须手动剔除周末两天提交。

### 周报的三条硬性口径（生成时逐条对照）

**1. 文件名用「周一~周日」标签，正文按工作日口径。**

历史周报文件**全部是周一~周日**的区间标签（`周功能总结-MMDD-MMDD`，末段为周日），但正文覆盖的是工作日。因此文件名跨到周日，正文与数据只算周一~周五，并在头部用一句话说明周末去哪了。示例写法：

> 覆盖 5 份日报：MMDD…MMDD。**正文区间按工作日口径取 M/D–M/D**；周六无提交，周日未到。
> 上一个周末（周六，22 笔）已计入上一版周报…**本版只取其中的 45 笔**，不重复计入该周六。

若上一版周报已把某个周六计入其自身，本版必须显式声明不重复计入——否则同一批提交会被两份周报各算一次。

**2. 改动量口径要先扣掉「文档/测试治理」再下结论。**

功能域里常混入大额删除（文档收敛为单一事实源、清理联调期证据、移除低价值测试）。逐域统计后必须检查该域是否存在单笔删除量异常的提交，并在该节末尾给出「剔除后」的真实净变化，例如：

> 该功能域合计 +A / −B（净 +N）。其中文档与测试治理贡献约 M 行删除（三笔）。把这三笔剔除后，功能性改动为 +A' / −B'（净 +N'）。

不要直接拿含文档收敛的净变化去描述功能进展。

**3. 去重说明要区分「patch-id 重复」和「同主题不同 patch-id」。**

- patch-id 相同：按 `dedup.integration_branches` 判定代表侧，列成「保留 / 剔除」表。
- **patch-id 不同但主题完全相同**（同一改动在实现分支与集成分支上各有一版，内容差几行）：**不会被自动判重**。必须单独写一段说明它两笔都计入了，并给出「若要按同目的只算一笔，可人工剔除 X，总数则为 N−1」。漏写这句会让人以为重复计数。

### 周报落盘后的自检（必做）

1. 按功能域归并时，**一笔提交只归一个域**，且「笔数 / 文件 / 新增 / 删除」四列的合计必须与总数逐列相等；用脚本重算一次，不要手算。
2. 用脚本抽出正文里所有反引号内的 7~8 位 hash，逐个核对是否属于本周提交集合（包含被 patch-id 剔除的那些）；出现集合外的 hash 要人工确认它是不是被引用到的历史提交（如「某笔 revert 掉的那个 commit」），确认后保留，否则是笔误。
3. 按天表的提交数之和必须等于总数；各天若有跨仓提交，注明当日主线。
4. 章节内互相引用的小节号（如「见 §17.1」）要在增删章节后重新核对一遍。

### 周报·一页纸小结（向上汇报口径）

周报正文很长（按功能域逐笔列），汇报时另出一份**一页纸小结**：读一分钟能说清「做了什么、到哪一步」。

**触发**：用户说「把周报简短总结下」「写进周报的总结」「汇报用的版本」时，在周报正文**最前面**插入 `## 本周小结` 一节（头部元信息 blockquote 之后、`## 0. 口径与术语` 之前）。

**模板**

```markdown
## 本周小结（M/D–M/D）

<项目名>本周主要推进 N 件事：

- **<事项>**：<原来什么状况>，现在<变成什么样>，<谁因此省了什么 / 多了什么能力>。（**<进度>**）
- ……

另有 M 件收尾：**<事项>**（<一句话>）（**<进度>**）；**<事项>**（<一句话>）（**<进度>**）。

> 统计范围：<按 report_scope 声明的范围>
> 进度口径：`开发中 → 开发完成 → 联调中 → 测试中 → 已上线`；合入主干即记「已上线」。
```

**硬性规则**

1. **只写「事 + 进度」**。不写提交笔数、不写分支名、不写 MR 编号、不写评审状态、不写风险与卡点。
2. **每条必须回答「所以呢」**：写完问一句「这给谁省了什么事」，答不出来就删。
3. **主语是「人能干什么」**，不是「模块实现了什么」。
4. **有数字就用数字**：写「从 5 步减到 1 步」，不写「大幅简化」。但**不写提交笔数**。
5. **篇幅**：主项 5±1 条，正文 ≤ 500 字，一分钟读完；次要事项合并为末尾一句。
6. **不暴露内部风险**（MR 无人评审、分支未合、环境陈旧等）——这些留在正文的「需要留意」节，不进小结。
7. **进度取该事项全部提交里最靠后的那个阶段**，不是平均、不是最新一笔。
8. **假定读者没参与过这次开发**（读者通常是 +1 / +2）。出现内部平台、系统、产品名时，**必须紧跟一句话说清它是做什么的、谁在什么场景用**，不能只甩名字；出现工程术语（接口、上游、网关、分支、diff、MR、模块拆分、镜像、部署拓扑）一律换成**结果语言**——读者只关心「原来怎样、现在怎样、省了谁什么事」。

**禁用词**（AI 味重，一律改写；同义变体一并禁）

> 赋能 / 闭环 / 抓手 / 助力 / 全面提升 / 深度 / 彻底 / 杜绝 / 显著提升 / 有效解决 / 大幅优化 / 不仅…而且 / 值得注意的是 / 综上所述 / 标志着 / 意味着

**内部系统 / 平台名的写法**（读者多半不知道它是什么）

涉及内部平台、系统、产品时用三段式，不要只甩名字：

> **<平台/系统名>**（<一句话：谁在什么场景用它>）：原来<人工或麻烦的做法>，现在<自动或简化的做法>。（**<进度>**）

- 名字可以留（它是对接方的共同语言），但那半句「它是干什么的」**必须**有。
- 名字后面**不要**接工程细节（模块拆分、镜像、进程模型、部署拓扑、接口 / 上游）——这些属正文，不进小结。
- 拿不准读者知不知道，就默认不知道。

**黑话 → 人话（示例，按需扩）**

| 别写 | 改写成 |
|---|---|
| 裸系统名（`<系统名> 后台`） | 权限后台（管理谁能用哪些功能） |
| `QA` | 测试环境 |
| `上游` / `接口` / `网关` / `代理登录` | 说结果：地址从哪来、数据口径是什么、用户在哪点 |
| `MR` / `分支` / `提交笔数` / `diff` | 删除（见硬性规则 1） |
| 内部简写 `xx端` | 全称 + 它管什么 |

**进度词表（固定六个，按递进）**

| 进度 | 判定依据 |
|---|---|
| 开发中 | 分支持续有提交，功能面未闭合 |
| 开发完成 | 功能写完并自测，尚未合入集成分支 |
| 联调中 | 跨仓 / 前后端对同一功能各自落地，接口在对接 |
| 测试中 | 已合入集成分支（`dedup.integration_branches`）或已部署测试环境 |
| 已上线 | 已合入主干（`git merge-base --is-ancestor <sha> refs/remotes/origin/HEAD`） |

> **「已上线」以合入主干为准**（用户口径），不额外查发布记录。若某件事实际未发到生产，由用户口头更正，不自行推断；也不要反过来把「合了主干」降级写成「待上线」。

**统计范围**

小结（及一切向上汇报）只覆盖 `config.report_scope` 声明的目录，通常为主项目根；个人配置仓、知识库仓不计入。范围变更只改 `config.json`，不改本节。某仓本周 0 提交时，在小结里不出现，也不列「0 提交」行。

**与正文的关系**

正文（功能域逐笔）是完整事实源；小结是它的**向上汇报投影**，只取价值最高的 5±1 条，不要求覆盖全部提交。两者条数对不上是正常的——**不能拿小结的条数去凑正文的笔数**。

### 公司周报（公司模板口径）

公司（或其他对外交付对象）若另有**固定格式的周报模板**，按本节的写法另出一份。**它与个人周报并存，不替代、不改动个人周报**。

**触发**：用户说「生成公司周报」「按公司模板出一份」「给公司的周报」时。

**与个人周报的关系**

| | 个人周报（周功能总结） | 公司周报 |
|---|---|---|
| 用途 | 自己的完整工作记录与事实源 | 交付给公司 / 上级的格式化周报 |
| 格式 | 按功能域逐笔，可很长 | 公司模板三段式，通常一页 |
| 数据 | 全量提交 | **从个人周报投影**（小结 + 正文《需要留意》《状态与风险》） |

**素材**：**直接取同期个人周报**，不重新采集（见《周报生成流程》）。**时间栏取与个人周报同一区间**，保证两份口径一致。

**输出**：写入个人周报**同一目录**，文件名 `公司周报-<起>-<止>.md`（如 `公司周报-0921-0927.md`）。

> ⚠ **只落本地文件，不要写进在线文档**（飞书 / wiki / 在线表格等）。用户的流程是「生成到本地 → 自己复制粘贴」。除非用户这次明确让你写，否则不在线上动手。

**模板**

```markdown
# 个人工作周报

部门：<团队 / 小组名称>
时间：M月D日 - M月D日

---

## 本周工作内容

| 重点工作 | 关键进展 | 风险及应对措施 |
| --- | --- | --- |
| <事项> | <原来怎样 → 现在怎样；多个要点用「；」连成一行> | <可外报的卡点 + 应对；无则写「无」> |
| …（4–6 行） | | |

---

## 其他收尾

- **<事项>**：<一句话>。（<进度>）

---

## 本周重点日程

> 【待填】公司模板此处由在线日历卡片同步，本地无日历数据源。

---

## 下周工作计划

- [ ] <任务>。负责人：<…>，截止时间：<…>
```

**字段映射**

| 公司模板字段 | 取自 | 要点 |
|---|---|---|
| 重点工作 | 一页纸小结的「事」 | 一条一事 |
| 关键进展 | 同件事的「原来 → 现在」 | 单元格**保持单行**，多个要点用「；」连——换行或 `<br>` 粘到在线文档里容易坏 |
| 风险及应对措施 | 正文《需要留意》里**可外报**的部分 | **只写对外的卡点与应对**（如「功能已在测试环境验证通过，等待评审合并，按排期推进」）；**内部矛盾不上报**（无人评审、分支未合、环境陈旧、MR 挂了多少天）；无则「无」 |
| 本周重点日程 | **无本地数据源** | 留占位，由用户手工粘贴 |
| 下周工作计划 | 正文《状态与风险》里的未完成项 + 待决策项 | 给建议即可，**负责人 / 截止时间一律留占位**，不替用户编 |

**硬性规则**

1. **不改个人周报**：公司周报是另出的一份，两份并存。
2. **落本地、不写在线文档**（见上）。
3. **统计范围**与小结一致（`config.report_scope`）。
4. **说人话**：公司读者同样没参与开发，适用小结的硬性规则 8 与《内部系统 / 平台名的写法》。
5. **表格单元格单行**；要点用「；」连接。
6. **风险列克制**：写对外的应对与排期，不写内部问题。
7. **日程、负责人、截止时间不编**，留占位。
