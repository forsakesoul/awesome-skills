## 日报双版本（人读 / 明细）

**每次生成日报都产出两份**，写入同一目录（`<output_dir>/YYYY/M/第N周/`）。文件名与开关见 `config.daily_variants`；缺省如下：

| | 人读版 | 明细版 |
|---|---|---|
| 缺省文件名 | `MMDD.md` | `MMDD.agent.md` |
| 读者 | 本人 / +1 / +2（可直接转贴） | AI（生成周报、回溯查证）/ 需要精确定位时的人 |
| 篇幅 | **40–70 行**，一到两屏，3 分钟读完 | 不限（通常 200–300 行） |
| 内容 | 只写「**事 + 进度**」：今日主要进展 3–5 条、需要处理、备注 | 全量事实档案：速查索引表 + 逐笔明细 + 分支状态 + 票据对照 + 数据概览 + 去重与采集说明 |
| 禁写 | commit hash / 笔数 / 文件数 / 增删行 / 分支名 / ahead-behind / patch-id / MR 与工单编号 / 评审状态（**「需要处理」区例外**） | 无（越精确越好） |

**生成顺序固定：先明细 → 后投影人读。** 人读版是明细版的**投影**，不是第二份独立手写稿——两份共用同一份事实，条数**不要求对应**（3–5 条人读版覆盖 40 笔明细是正常的，不能拿人读版条数去凑笔数）。

**布局兼容**：历史归档（本工作区为 **2026-10-07 及以前**；10-08 起为双版本）是旧布局，**只有明细、没有同名人读版**，且明细占用了主文件名——读取时按「`MMDD.agent.md` 优先，缺失回退 `MMDD.md`」处理，不要因为找不到人读版就重采或报错。

## 日报生成流程

1. **收集提交**: 使用 `scripts/collect_commits.py --date YYYY-MM-DD --timezone Asia/Shanghai -a <name> -a <name>` 对用户指定仓库（未限定时使用配置仓库）按精确自然日、作者条件采集；**多个作者必须写成多次 `-a`**（`-a 'a|b'` 在 Apple Git 下按 BRE 解析、`|` 被当字面量，静默返回 0 条且退出码为 0）；时区**默认已固定为北京时间**（不随本机系统时区漂移，本机切到美西也照样按 `+08:00` 归属）；脚本**默认覆盖所有分支**（等价 `--all`，且没有 `--all` 开关，多写会报 `unrecognized arguments`；只有 `--no-all`），保留脚本回显的时区与半开区间
2. **获取详情**: 复用采集脚本输出的 **author date** ISO 时间（`%aI`，带原始 `+08:00` 偏移）、提交信息及完整 subject/body，据此提取 Work Item ID；不要改用 committer date，重放会刷新它
3. **分支归属**: 对每个提交执行 `git branch -r --contains <hash>` 确定所属分支，取第一个非 HEAD 分支
4. **代码统计**: 执行 `git log --numstat --format=""` 统计增删行数
5. **Work Item 关联**（若 `workItems.enabled`）:
   - 对每个分支，从「分支名（去 `origin/`）」+ 该分支下所有 commit 的 subject/body 用 `id_patterns` 提取 Work Item ID；同时查 `branch_work_items` 手动映射
   - 按 Work Item ID 归并（同一需求跨仓/跨分支合并为一行）
   - 阶段判定：优先 `branch_stage_hints` 命中分支名 → 否则分支已合入 main 时按 `released_branch_hints`/`merged_to_main_stage` 归类 → 仍无则标「未分类」
   - 命中 `blocked_hints` 的加「⚠ 阻塞」标记；测试中阶段项下用 `[ing]`/`[done]` 标注子状态（依据 commit 类型/合入状态推断，无 API 时保守标 `[ing]`）
5b. **核对待办台账（跨日累积）**: 读 `config.todo_ledger.dir` 下**当前月份**的文件（`{YYYY}-{MM}.md`），把今天新发现的卡点 / 待决策 / 风险按《待办台账（跨日累积）》一节的规则入账，并据此决定「需要处理」（人读版）与「需要留意」（明细版）该写哪几条——**不是把台账整表抄一遍**
6. **按分支分组（主线 = 分支）**: 分组单位是「分支 + 仓」，**不是提交主题**。**一个分支当天只出一个章节**：同一分支里的多件事写在同一条主线内用要点分述，**不得拆成多个章节**——最常犯的错就是把同一分支的「看板交互」「接口适配」「导出权限」「出图服务」写成三四个主线。跨仓的同一需求（同一需求号 / 前后端配对）可合为一节、节内按仓分述；**无共同需求号的异分支不硬合并**（如纯文档分支与功能分支各自成节）
7. **生成明细版**: 按《明细版模板》输出全量事实（含**速查索引表**）
8. **生成人读版**: 按《人读版模板》从明细版**投影**出 3–5 条「事 + 进度」+ 需要处理 + 备注；**不重新采集、不逐笔重写**
9. **写入文件**: 两份都按 `config.daily_variants` 的文件名写入对应周子目录（目录不存在先创建）
10. **落盘后回读校验**: 明细版校验「每个 hash 均出现 + 各节条目数 = 标题声明笔数」；人读版校验「主项条数 = 生成的条数」且**无禁写字段**（grep hash / 笔数 / 分支名应无命中，`需要处理` 区的 MR 号除外）

**模板说明**

- **章节 = 分支**：每节标题就是一条分支（跨仓同一需求可合节），节内按时间逐笔列 commit，**不按工作类别再分组**。同一分支当天做的事再多，也只在同一节里用 `-` 逐笔写；**不要出现「一、图表交互」「二、接口适配」这种同一分支被拆成两节的情况**。「CI 修复」「文档补充」「测试覆盖」只能作为同一节内的某几笔，不能升格成独立章节。
- 同一类工作的多个提交合并为一条，用一句话概括；**commit 短哈希用反引号括起并 `/` 分隔**，方便回溯源码。
- 跨仓库同步的工作可合并为一个章节，并在节内分别标注各仓哈希（前提是它们属同一需求 / 同一功能）。
- **「索引」表放在正文最前**，一行一笔、覆盖全部提交——这是给机器和回溯用的速查入口，比散落在正文里的 hash 好定位。
- **「已合入主干」**小节按天汇总当天合入主分支的分支、merge 哈希与时间，附 MR 链接。
- **「分支状态」**小节记录每个分支领先/落后 origin、是否合入、是否推送，以及当天无提交的仓库标注「0 个提交」——这是日报价值的关键，不能省略。
- **「Work Item 关联」**小节（启用时）按 `stages` 顺序分组列出当天涉及的 Work Item，每条含可点击链接、关联分支与 commit 哈希；阶段为本地启发式，非 GitLab 真实状态。
- "数据概览"汇总所有仓库的提交数（实质 + merge 拆分）和代码增删；"一句话总结"给整体总结与可操作的后续建议。

### 人读版硬规则

1. **只写「事 + 进度」**。进度取固定六档：`开发中 → 开发完成 → 联调中 → 测试中 → 待上线 → 已上线`（**合入主干即「已上线」**）。事件不落某档时用中性词（「已整理」「已完成（本机）」「整理中」），不硬套档位。
2. **进展区禁写**：commit hash、提交笔数、文件数、增删行数、分支名、ahead/behind、patch-id、MR / 工单编号、评审状态。
3. **「需要处理」区允许点名 MR / 工单编号**——那是行动项，必须有可定位的标识。**这一条与规则 2 是刻意不同**，不要为了「统一」把编号也删掉。但**必须写成可点击的真实链接** `[短名#编号](地址)`，并且每条带上台账编号 `T-xx`（负责人可直接说「T-06 先不管」）；写成裸编号或反引号代码都算不合格。
4. **假定读者没参与过本次开发**：内部平台 / 系统 / 产品名首次出现**必须紧跟一句「它是干什么的、谁在什么场景用」**，不能只甩名字。
5. **工程黑话换结果语言**：接口 / 上游 / 网关 → 说清数据从哪来、用户在哪点；MR → 代码审查请求；diff → 改动；缩写 `QA` → 测试环境。对照表见 `weekly.md` 的《黑话 → 人话》。
6. **篇幅**：每条正文 **≤4 行**（一条主线可能覆盖整条分支的几件事，允许比旧版稍长），全篇 **30–70 行**；主项 3–5 条，超过 5 条把次要事项合并为末尾一句。
7. **一条主线一条**：人读版条目与明细版章节**一一对应**，都是「一个分支一件事」。同一分支的几件事（看板交互、接口适配、导出权限、出图服务）**必须写在同一条里**，不许拆成两条并列；条数超 5 时合并的是**不同分支**的次要线，不是把一条主线切细。
8. **数据只留「备注」两行**（数据 + 上线状态），不展开分仓 / 分时段表——那些在明细版里。
9. **禁用词**同 `weekly.md` 的《周报·一页纸小结》（赋能 / 闭环 / 抓手 / 助力 / 深度 / 彻底 / 显著提升 / 标志着 / 意味着 …，同义变体一并禁）。
10. **「需要处理」不是清单复读**：只报新增 / 有变化 / 阻塞未完成（见《待办台账（跨日累积）》）。同一件事连续挂三天且毫无变化时，**不写在日报里**——它已经在台账上，日报不再重复占版面。

## 待办台账（跨日累积）

**要解决的问题**：日报每天都会冒出「卡点 / 待决策」，其中很多是同一件事——环境没补、权限没 apply、MR 没人评审。如果每天都原样列一遍，一周围下来同一批卡点会重复出现五六次，版面被吃掉，真正的**新**问题反而被埋掉。所以「需要处理」不再是日报的临时段落，而是一份**跨日台账**在当天的投影。

**位置**：`config.todo_ledger.dir` + `filename`（本机真实路径写在 `config.json`，**该文件已被 `.gitignore` 忽略**），**按月一个文件**（如 `2026-10.md`）：当前月文件是工作文件，往月文件只读归档、不再追加。台账是本地运营数据，不进版本库，也不随日报一起归档。

```markdown
**编号水位**：已用到 `T-03`，**下一个可用 `T-04`**（新项取此号后把水位加一；不要复用已删除/已作废的号）。
```

**新月份文件的编号水位承接上月**，不从 `T-01` 重来——否则「T-07」在两个月里指两件事。

列的含义：

| 列 | 写什么 |
| --- | --- |
| 编号 | `T-01` 起顺序分配，**永久不变**。作废 / 完成 / 归档都不回收号，删行也不回收 |
| 状态 | `☐` 待办 / `☑` 已完成 / `⊘` 作废 |
| 首次 | 第一次进台账的日期（`MM-DD`，跨年写 `YYYY-MM-DD`） |
| 最后提及 | 最后一次**写进日报**的日期——当天没进日报就不改，用来判断「这件事已经多久没动静」 |
| 归属 | 票号 / MR 号——**必须是可点击的真实链接**（规则见《编号与链接》）；没有票就写仓库名或主线名 |
| 事项 | 一句话，写「要做什么」，不写背景 |
| 阻塞 | `是` / `否`。**判据：不做完这件事，当前主线就无法验收或上线**。是则日报天天出现 |
| 备注 | 变化痕迹：卡在哪、谁在等、解除了什么前置。已有进展追加到今天，不覆盖历史 |

### 编号与链接（两件必做的事）

**① 编号不可变。** 新项一律取文末「编号水位」里的下一个号，取完把水位 +1。**已用过的号（含作废、已完成、已归档）永不回收**——负责人可能隔两周说「T-07 做完了」，号被复用就会指错人。台账末尾固定留一行水位标记：

```
**编号水位**：已用到 `T-08`，**下一个可用 `T-09`**
```

编号同时写进日报：每条「需要处理」都带 `T-xx`，负责人看到日报就能直接说「T-06 先不管」「T-03 改完了」。

**② 链接必须能直接点。** 台账、明细版「Work Item 关联」、周报工单表里的票号与 MR 号，**一律写成 `[显示名](真实地址)`，不要只写裸编号**，也不要写成反引号代码（那样点不动）。显示名统一「项目短名 + `#`/`!` + 编号」（如 `project-a#7`、`project-b!101`），地址按 `config.workItems.gitlab` 的三项拼：

```
票：url_template             {base_url}/{project}/-/issues/{id}
MR：merge_request_template   {base_url}/{project}/-/merge_requests/{id}
项目：abbreviations[短名] 或 project_paths[本地目录] → project 全路径
```

- **ID 必须实测**：来自 `glab api` 返回或提交正文，**不许按上下文推测**；项目按 `abbreviations` 解析，解析不到就退回全路径写法（如 `group-a/project-a#7`），**不要猜归属项目**。
- **裸编号在多项目会撞号**（同一数字在不同仓各有票），所以短名不能省；同一行引用多个项目时逐个带短名。
- 已关闭的票不再算「待办」：先查状态再入账，别把 `merged` 的 MR 挂在「待评审」里。

### 按月拆分与结转

台账**按月一个文件**，不写成一个越滚越大的单文件：

```
<todo_ledger.dir>/
  2026-10.md      ← 当前月（工作文件）
  2026-11.md      ← 次月
  2026-09.md      ← 往月，只读归档
```

- **读**：只读**当前月份**文件。找不到当月文件（且目录里已有上月文件）说明跨月了，走下面的结转。
- **编号跨月连续**：水位写在每个文件的末尾，新月份文件的水位**承接上月**。换月后第一项的号接着上月往后排，**绝不从 `T-01` 重来**——否则「T-07」在两个月里指两件事，「编号不可变」就废了。
- **结转（每月一次，在当月第一份日报生成时做）**：
  1. 新建 `<YYYY-MM>.md`，文件头写清所属月份与规则（照抄上月文件顶部说明即可）。
  2. 上月所有 **`☐` 未完成项整行搬入**新文件，「编号」与「首次」**原样保留**，「最后提及」保留（换月本身不算「有变化」）。
  3. 旧文件里这些行删除，在原位置留一行说明：`> 上月未完成 N 项已结转至 <YYYY-MM>.md`。**`☑` / `⊘` 行留在原月文件里**，作为历史归档，不搬。
  4. 水位行跟着搬，只在新文件里维护。
- **为什么按月**：一个月下来新增 / 完成能到三四十行，全塞一个文件后翻查成本高、diff 也糊；按月拆之后往月文件天然是「已结束月份的快照」，月底想复盘直接看当月文件即可。
- **不搬跨月的历史完成项**：已完成的留在完成那个月，避免「当月文件里全是陈年旧账」。


1. **读**：先读台账（不存在就按上面的格式新建，见《首次建立》），记下当前编号水位。
2. **比对**：把今天采集与查证中发现的卡点逐条与台账比对——
   - 台账里没有 → **新增**：按水位取号、水位 +1，追加一行，首次 = 最后提及 = 今天，阻塞按上面的判据定。
   - 台账里有、今天有变化 → **更新**：改最后提及为今天，备注追加变化（不要让备注互相覆盖）。
   - 台账里有、今天没动静 → **不动**：最后提及保持原值，**不进今天的日报**。
   - 台账里有、今天发现已完成（合入主干、票关闭、环境已补） → **完成**：状态改 `☑`、事项加 `~~删除线~~`、写完成日期，从「待办」移到「已完成」表，**编号跟着走、不改不回收**；**当天日报要报一句「已解除」**。
3. **投影**：按下面三类决定日报写哪几条。
4. **回写**：保存台账。**只改状态与备注，不删行**（除超过 `archive_after_days` 的归档）。

### 日报只呈现三类

`config.todo_ledger.report_only` 定义了这个白名单，缺省 `["new", "changed", "blocking"]`：

| 类别 | 判据 | 日报里怎么标 |
| --- | --- | --- |
| `new` | 今天首次入账 | 直接写，不加前缀 |
| `changed` | 已有项今天有进展 / 新增约束 / 阻塞升级 | 标「**有变化**」 |
| `blocking` | 未完成且阻塞=`是` | 标「**阻塞中**」；即使今天毫无变化**也要写**——它挡着验收/上线，漏掉代价比重复大 |

其余未办项（`☐` 且非阻塞、今天没动静）**一条都不写**，在「需要处理」区末尾用一行汇总：

```
另有 N 项历史待办未动（阻塞 M 项），见 <台账路径>
```

**为什么阻塞项要天天出现**：非阻塞项重复只是费版面；阻塞项漏一次，就可能出现「功能做完两周、验收从没跑过」这种情况。

### 首次建立

台账当前月文件不存在时，先判断是「第一次建立」还是「跳月」：`config.todo_ledger.dir` 里已有往月文件 → 按《按月拆分与结转》把未完成的 `☐` 行搬过来（编号水位承接上月），不要从 `T-01` 重排；目录也空 → 下面从头建：

1. 读目标日之前最近几份日报（明细版优先）的「需要留意」/「需要处理」段，抽未解决项。
2. 读 `config.json` 的 `branch_work_items`（`stage` 里写着卡点的）、`workItems.unmapped`、以及最近关闭但留有遗留项的票。
3. 同一件事在不同日期写法不同的，**合并成一行**（按「归属 + 动作」判重），首次取最早日期，备注里保留各次表述的差异。
4. 每条归往前先用 `glab api` 实测票 / MR 的当前状态（`opened` / `merged` / `closed`），再拼真实链接；已关的不入待办表。

### 与周报的关系

周报的「风险及应对措施」列从台账取（**跨月看多份月份文件**，只取本周涉及的那些），但同样只取当周有变化的 + 阻塞未完成的；一周内毫无动静的非阻塞项不占周报表格，只在周报末尾一行「台账另有 N 项未动」带过。周报里的票号 / MR 号同样是可点链接。

## 数字口径的硬规则（适用于明细版）

- **净改动为负（删除多于新增）时，必须在报告里解释来源**：最常见的是删除已入库的**生成产物**（构建产物、验证快照、导出的表格、缓存清单）或**一次性资产退役**（跑完的迁移脚本、被台账合并的旧文档）。此时要同时给出两个口径——「含删产物的原始改动」与「剔除该笔后的实际改动」——否则会被误读成「删了很多代码」，也会让工作量看起来比实际小。
- **时间表述一律落到可核的绝对事实**：写「N 年前 / 多年前 / 上个月」这类相对时间前，必须回查**仓库最早提交**与该文件的**首次出现日期**（`git log --reverse --diff-filter=A -- <path>`）。项目往往起步不久，凭印象写「一年前」会错得离谱。
- **去重核对项固定四类**：同远端重复（多个目录指向同一仓库，注意符号链接）、patch-id 副本（集成分支 cherry-pick / rebase 重放）、stash 自动提交、merge 提交。**若项目使用 worktree**，另需确认 detached worktree 本日是否产生新提交——这类提交可能**不被任何 ref 承载**，`git log --all` 采不到，须用 `git cat-file` 直读补回（对象在 `gc` 后会消失），并在报告的去重说明里明确交代结论。
- **「当日进集成分支」不等于「当前在集成分支上」**：共享集成分支（见 `dedup.integration_branches`）常在**次日凌晨**还有合并动作，会把当日最晚几笔一并带入。若直接按快照时的 `refs/remotes/origin/<集成分支>` 判定，会把跨日动作算进当天。正确做法是用**当日最后一次合并提交**为界逐笔做 `git merge-base --is-ancestor <sha> <当日末次合并>`，正文把「当日已进 N 笔」与「次日 M 笔随合并进入」分列，并在分支状态里交代这次跨日合并。
- **同一缺陷跨仓各改一次，不是 patch-id 重复**：A/B 两面或多仓副本对同一缺陷各提一笔时，因**文件路径不同，patch-id 不同**，须计为两笔（例：canvas backing store 取整修复在页面壳与注入脚本各一笔）。去重前先看 subject 与改动文件，别只看标题相同就判重。
- **`git fsck --dangling` 噪声极大**，长期使用的仓动辄数百条，且绝大多数是 `git stash` / autostash / lint-staged 备份对象。判断「有无无 ref 承载的功能提交」时，要按 author date 过滤后**看 subject 是否为 `WIP on …` / `On …: autostash`**，不能按条数下结论。**带真实 subject 的游离对象要先看提交正文**：若它是某实际提交的**改写前身**（与最终提交 `parent` 相同，或同一 author date），属被主动撤回 / 改写，**不得补回**。
- **远端不可 fetch 时要在报告头部显式声明口径**：若 `git fetch` 失败（内网 SSL / 断网），分支状态只能取自本地 ref、且**无法核实主干是否被他人推动**；此时 MR / 工作项状态改用浏览器同源 API 实读，并把「哪部分取自本地 ref、哪部分取自实时实读、时间点各是什么」写进头部说明，不要默认可信。
