# 归属、去重与 Work Item 规则

采集之后、写报告之前逐条对照。这里的规则决定一笔提交算不算、算到哪一天、算到哪条分支和哪张票。

## 日期归属

- **按 author date（`%aI`）归属**：`git log --since/--until` 只按 committer date 预筛，rebase / cherry-pick 重放会刷新 committer date。采集脚本已用 `%aI` 归属，并把预筛窗口前后各放宽 `SLACK_DAYS`（7 天）后在 Python 侧精确裁剪。不要改回 `%cI`，也不要把 git 原始 `--since/--until` 的结果直接当归属日期，否则重放当天会把旧工作重复计入。
- **一律按北京时间**：脚本默认 `Asia/Shanghai`，与本机时区无关。手写 `git log` 必须带 `+08:00` 偏移（`--since="2026-10-20T00:00:00+08:00" --until="2026-10-21T00:00:00+08:00"`），裸日期会按本机时区解释，边界提交归错天。判断当前北京日期用 `TZ=Asia/Shanghai date '+%F %T %z'`，不用本机 `date`。报告头部的时区与半开区间照抄脚本回显。
- **半开区间 `[当天 00:00, 次日 00:00)` 是事实边界**：区间外的提交不写进当天，相邻日期（含周末）的提交也不并进来。周六、周日的提交各归各自那一天；该周末没出日报就留缺口，要补就单独出那一天的日报。周报的统计区间按各版次约定，但周末提交同样按其自然日归属，不为了凑"纯工作日区间"挪到周一。

## 作者过滤

- **多个作者写成多次 `-a`**，脚本会为每个 `-a` 追加一个 `--author`，多次即 OR。手写 `git log` 同理用 `--author=a --author=b`。
- `-a 'a|b'` 在 Apple Git 下按 BRE 解析，`|` 被当字面量，结果是 0 条、退出码 0、无报错；脚本遇到未转义的 `|` 会在 stderr 报警。**采集结果为 0 时先怀疑这条**，再下"当天没提交"的结论。
- 只纳入 `config.author.patterns` 匹配到的作者（个人视角）；要团队视角时临时放宽并说明。

## 覆盖范围

- 脚本默认覆盖所有分支（等价 `--all`，只有反向的 `--no-all`，多写 `--all` 会被 argparse 拒绝）。不覆盖所有分支会漏掉 worktree 和未合入 feature 分支的提交。
- 配置的仓库不在同一个父目录下时，必须把路径都显式传进采集脚本，否则会静默跳过。
- 某仓无提交仍要列出并标"0 个提交"。它只表示该日期、时区、作者和仓库集合下没有匹配的 commit；输出前确认已覆盖全部配置仓库且未用 `--no-all`。未提交改动、设计、QA、验收和沟通另列为"非提交活动"，不得据此写成"当天没有工作"。
- 分支名取远端分支简称（去 `origin/`），worktree 分支按实际分支名。代码统计只统计文件变更，不含 merge commit。

## 跨分支去重

`--all` 会让同一改动在集成分支上的 cherry-pick 副本各算一次。用 `git patch-id --stable` 比对：patch-id 相同只计一份，报告的去重说明里逐组列出"保留 / 去重"的 hash 对；同名同目的但 patch-id 不同（改动量有差）要各计一笔。

**代表侧（保留哪一侧）按优先级**：

1. 保留不在集成 / 重放分支上的一侧。集成分支是 cherry-pick 的目的地，取它会把工作记到集成分支的语境里。
2. 两侧都不在集成分支时，保留已合入主干的那侧。
3. 一侧被分支或远端承载、另一侧只存在于 worktree 的 detached HEAD 或 reflog（`git branch -a --contains` 为空），保留被分支承载的一侧，不按时间先后选到没有 ref 指向的那份。
4. 仍并列时保留 author date 靠前的。

原则是"保留实现分支、去重重放分支"，比较的是分支名而不是时间先后。集成 / 重放分支名列在 `config.dedup.integration_branches`，生成时按该列表判定，不硬编码分支名。

排查无 ref 的副本：`git branch -a --contains <sha>` 为空但 `git show <sha>` 能跑，通常是 worktree 的 detached HEAD（`git worktree list` 可见）；两份 sha 的 patch-id 和父提交都相同时，确认哪一份才是被推送的。

## 同一远端多个 checkout

两个本地目录可能指向同一个远端（主仓 + 验证仓，或改名后留下的旧 checkout），`--all` 会让同一批提交各算一次。采集后按唯一远端只计一份并在报告中注明；目录组记进 `config.dedup.same_remote_paths` 供下次直接引用。

## 章节按分支、票据按提交

- **报告章节和人读版条目一个分支一条**，不按提交主题拆。同一分支当天做了几件不同的事，只能写在同一条主线内用要点分述。跨仓的同一需求（前端 `master` + 后端 `feature/*`，或多仓同名分支）可合为一节、节内按仓分述；没有共同需求号的异分支不硬塞进同一节。
- **票据归属逐笔判定**：`branch_work_items` 只是"该分支主要归属"的补充，不等于该分支每一笔都属这张票。同一分支里既有票据内工作又有无票的独立收尾时，归拢表里逐笔拆开。

## Work Item 跨项目

提交正文里的引用不等于本仓项目的票据：代码仓在一个项目，正文引用的可能是相邻项目的票或反馈项目的 QA 票（本机未必有 checkout）。

- 解析顺序：① 正文自带全路径（`group/project-b#12`）或 `Refs: <base_url>/<project>/-/work_items/<id>` 尾注，直接采信；② 裸 `#NN`，按正文描述与该编号的标题逐字比对后再归属；③ 只有主题相符、标题对不上的，标为待确认，不写进映射。
- 裸编号会跨项目重号。默认把 `#NN` 落到本仓项目是错的，归属必须显式写 `project`；查编号至少覆盖本仓项目和已知可能承载该主题的相邻项目。
- 正文里还有大量不指向 Work Item 的 `#NN`：MR IID、十六进制色值、代码 / 样式引用。进映射前先判断它是不是票据号。
- 一个分支可对应多张票据（QA 反馈批次常见），用列表而不是硬塞一张；一张票据也可能横跨多个项目与分支，在 `note` 里写清拆分关系。
- 阶段判定是本地启发式（分支名关键字 + 合入状态 + `branch_work_items` 映射），不是 GitLab 真实状态；未检测到 ID 的分支归"未分类"或靠映射补全。

## 落盘与校验

- 周目录不存在就直接创建，路径形如 `<output_dir>/YYYY/<M>/第N周`（月份无前导零、周次中文序数，如 `2026/9/第三周`）。
- 长文件分段追加，不一次写入；宿主对大文件写入有限制时按本地备注处理。
- **落盘后必须回读校验**：采集清单里每个 commit hash 都出现在文件内（缺失即漏笔），并用正则统计各章节的 `- **\`hash\`` 条目数与标题声明笔数、总数一致。
